Nothing — this is the Shop exactly as it ships, and the harness's own proof that a screen the game already draws is expressible here.

The worked example, and the harness's own proof: the column is at OFFER_SHOP_LAYOUT's shipped numbers (col_x 820, col_w 392, col_y0 72, card_h 92, pitch 104), so opening this beside docs/ui/shots/<branch>/13-shop.png should read as the same screen. If it does not, the harness is lying and that is the bug — not the mockup.

The galleon is blocked in, deliberately. She already exists and already looks right; redrawing her in CSS would be a worse copy of a solved thing, and every minute spent on it is a minute not spent on the half of the screen that is the question. A block that stands where she stands leaves the column the right amount of screen.

The one literal hex here is the interesting case. .card--dear is #dfce9d, which is parchment with every channel multiplied by 0.95 — what colour_shade does in Odin, and what CSS has no operator for. check-mock.py allows it for exactly that reason and names the swatch and factor it resolved to, so the port is a colour_shade call rather than a new swatch. A hex that is not a shade of anything on the roster fails, which is the whole point.
