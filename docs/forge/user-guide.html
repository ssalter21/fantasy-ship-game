Getting in

Four ways to start it, all the same build.

FromDo this
ExplorerDouble-click scripts/forge.cmd. It forwards to run.cmd -Forge, so the build command lives in one place.
cmd.exescripts\run.cmd -Forge
PowerShellscripts/run.ps1 -Forge
Anywhereodin run cmd/forge from the repo root

The window opens at 1760 × 1000 and refuses to be squeezed below 1280 × 760 — under that a pane stops being able to show its columns. It is genuinely resizable; every pane lays itself out from the window's current size rather than from a designed canvas.

What it is not

The Forge never writes to your source tree. It reads the live tables by calling their own accessors at startup, and it hands work back as text on your clipboard. Closing the window discards the session — there is no save file and no autosave.

It also never imports presentation/, which is a compile-time fact rather than a convention: editor widgets cannot leak into a game screen, and none of this links into the shipped exe. That is also why it looks nothing like the game — the Forge is deliberately exempt from docs/ui/style-guide.md.

How editing works

There are no apply buttons, no confirm dialogs, and no save. Understand this bit and the rest of the tool follows.

Each frame, in this order:

  1. Restore — an undo or redo, if you pressed one, so stepping back is never itself recorded as an edit.
  2. Snapshot — the content as it stands, held for comparison.
  3. Draw — every control writes straight into the content it is showing. Type a digit and the budget panel beside it has already recomputed.
  4. Record — if anything moved, the new state is pushed onto a 64-deep undo ring of whole-content snapshots.

Every edit being reversible is what buys the absence of confirm dialogs. Nothing asks "are you sure", because Ctrl+Z is always the answer.

Refusal, not rejection

Core's authoring helpers assert on the rules that make an item well-formed. A tool that let you assemble an illegal effect and only found out on emit would crash on your work — so the Forge asks the same questions at the keystroke, keeps the old value when the answer is no, and writes the rule you broke to the status bar in red.

The check is always taken of the whole candidate tree, never of the node you touched. An edit deep in a tree can make an ancestor illegal — swap a Const for a Captains_Order reading and the Mul above it becomes arithmetic over the captain's order, which is not allowed.

Committed trees are reassembled by calling core's own expr_* helpers, so an ill-formed tree is unrepresentable rather than merely rejected.

Driving it

Mouse-only is treated as a failure state. Focus is a first-class thing here, not a raygui afterthought.

Tab and Shift+Tab walk every control in draw order and wrap around. The focused control is outlined in the accent colour and takes the arrow keys, Space and Enter for itself. Clicking a control also gives it focus. Switching surfaces puts focus back at the top of the form.

The status bar

Bottom-left tells you what the focused control does. When an edit is refused it turns red and names the rule; when you copy, it turns green and reports the byte count. Bottom-right is a permanent reminder of the accelerators, with live undo and redo depths in brackets.

1 · Item Workbench

The roster as a table, one item's whole authored field set beside it, and its power budget beside that — all three at once, because balancing is comparing an item against its neighbours and against its allowance at the same time.

The roster pane

Type in the filter box to match names by case-insensitive substring — "deck" finds "Deckhands", "Deck Cannon" and "Deck Pumps". Four facet combos narrow further by tier, slot size, tag and verb; each starts at any. Faults only reduces the list to rows roster_check reports a fault for.

The sort combo offers roster, name, tier, size, weight, cost and fault order. Roster order is the default and is not a preference — it is the order an Offer and a shop index the table by, so it is the order you reason about seeds in. Every other key reorders the view alone; the # column keeps showing the roster index throughout.

Table columns
#The roster index — what a seed draws by.
itemName, then tier/size, then tag initials.
wtAuthored weight.
fxEffect count.
costThe budget cost, coloured by verdict. The stripe down the left of the row is the same verdict.

Under the table, items per grant cell counts the roster into the size × tier cells the budget licenses it by. A cell holding fewer than three items turns amber: it cannot vary what it deals, which is a thin shelf for an Offer or a shop to draw from. That is a warning, not a fault.

+ append item adds a row at the end — a Splash-tier, Small, Artifact-tagged "New Item" with one Phase_Contribution effect paying 1. Appending is the only growth the roster admits; see Traps for why.

The item field set

This pane is closed: it shows exactly what a Fitting authors and nothing else.

Below the rule, four derived read-outs: capacity (contribution − bulk), speed cost (weight/10, subtracted from effective Speed), shop cost (by tier, in cargo) and fitting weight. None are yours to set.

Effects

A fitting carries up to three. Tabs pick which one you are editing; add appends a new Phase_Contribution paying 1, and remove disappears at one effect, because an item with none fails the effect-count band.

Authored

verb — what the resolved magnitude does, and so which consumer reads it.

timing — when the effect resolves at all across a battle.

synergy — an optional selector that scales the magnitude by the count of matching fittings. Pick an axis, then the criterion on it.

Derived

phase — read off the verb.

site scale — 100 for everything you author; only a Fight site moves it.

timing, when the verb is Modify_Speed — locked to Always, with the reason attached.

A lock, not a bounce

Choosing Modify_Speed sets the timing to Always rather than refusing whatever the effect happened to be firing on. You get the verb you asked for; the timing control then renders as locked.

The magnitude tree

The tree is drawn as its prefix walk, indented by structure, one editable row per node. The left gutter names each node's role in its parent — a Gate reads if / vs / then / else, a Sub reads from / less, a Pct reads value / percent — so four subtrees read as a condition and two branches rather than as four anonymous rows.

The kind combo on each row re-kinds that node, carrying across whichever children the new arity still has room for and filling the rest with a zero constant. That is what makes the kind control an edit rather than a reset. Each kind then shows only the payload it reads: a literal value, a quantity, a selector plus its criterion plus a side, or a comparison operator. A Pct node's divisor renders as a derived /100 — it is the language's only division and is pinned.

Above the tree, a live node count. The bound is EXPR_MAX_NODES, and because every arity is even, the largest well-formed tree is one node below it. The counter turns amber when you reach that edge.

Presets

Five composed shapes from expr.odin are offered as one-click subtrees. Pick one, set its parameters, select the node you want to replace, and press insert here.

What a preset drops is ordinary nodes, still editable. It is a starting point, not a closed set you must choose from — and a subtree that still matches a preset when you copy emits as that preset's helper, so the roster keeps reading like the roster.

The power budget

Rendered as the equation, never as a verdict, because the formula has no optional term: you rearrange it for the magnitude you may spend rather than guessing a number and asking whether it passed. Every term prints with its source beside it and its value right-aligned on the mono step, so the column reads as a sum.

What the panel shows, top to bottom

Allowance — grant (from size base, size rank and tier), weight allowance (your weight against the size default), their sum, and the two-sided band around it.

Cost — the capacity option, then one line per effect reading peak × rate × factor, then the total.

Verdict — clean, or the fault plus which stage of the check it stopped at. The check short-circuits, so a structural fault hides a band fault and the panel says which one it is looking at.

Solve for magnitude — the inverse. With size, tier, weight and effect shape pinned, it reads back the peak range that lands inside the band, and the tree peak that implies once synergy and any ramp cap are taken off.

Pricing census — the counts every synergy selector is priced against, derived by walking the real ship template.

Under each effect line the panel explains why it priced that way. For Repair it says whether the effect earned the burst rate and how — by frequency, or by a gate on one of the two quantities that can turn off again inside a fight. For everything else it names the gate rules that actually fired, walking the path the magnitude rides rather than reporting the first Gate it sees.

The trap the panel shouts about

A tree whose magnitude is a quantity read outside a gate's comparands peaks at zero — so the budget has no bound to charge against, and prices at nothing an item that pays out every round. The panel flags this in red. It is a finding about your tree, not a refusal: the shape is legal, it is just free.

Three readings of the tree

The same tree answers three different questions, and you need all three at once:

ReadingAnswers
expr_evalA real round, against the probe context below the panel — which you can poke.
expr_showcaseEvery gate open, every count 1. This is the number the item card shows the player.
expr_peakEvery gate at its larger branch, every count at its peak. This is what the budget charges for.
effect peakThat peak, ramped, site-scaled and multiplied by the synergy count.

The probe starts at a plausible mid-battle round rather than a context of zeroes — half hull, starting speed on both sides, round 1, every own-census count at 1 — because a context of zeroes answers every gate with "shut" and makes every item read as doing nothing. Edit any quantity, and switch the census combo between Own and Opponent to edit either side's counts.

Encodings, printed under the probe: order is Hold 0, Press_Brace 1, Press_Fire 2, Commit 3; visibility is Exposed 0, Concealed 1.

Why an edit is refused

Seven rules. Each is an assert in core's authoring helpers, asked here at the keystroke instead. The status bar prints the rule, phrased so you know what to author instead.

FaultThe rule, as the tool states it
Node_Bound_OverrunThe tree is bounded at EXPR_MAX_NODES, and every arity is even, so one below that is the largest well-formed tree.
Speed_Reads_SpeedA Modify_Speed tree reads no speed: Speed is the layer it is an input to.
Order_Is_Not_A_ScaleThe captain's order is an encoding: match the bare reading with Eq or Ne, and do no arithmetic over it.
Speed_Carries_A_TimingA Modify_Speed effect is Always: its consumer is read off the battlefield, where no counter exists.
Peak_Output_Over_CapA gated effect's peak output is capped: a gate discounts the price without shrinking the number that lands.
Cadence_Not_PositiveTiming_Every_N wants a cadence of at least one round.
Charge_Not_PositiveTiming_Charge wants a positive cost and a positive gain.
The subtle one

Order_Is_Not_A_Scale also catches a reading buried inside a Gate's comparand — max(order, 2) == 2 is the same forbidden sentence through the arithmetic door, and nesting a Gate inside a Gate's comparand is the one way the tree editor can reach it. A comparand that reads the order must be the bare reading, even under Eq.

2 · Encounter Builder

A recipe is a name plus an order over stage specs, and a stage spec is a kind plus an optional stock pool. That is the whole authoring alphabet, so the builder edits exactly that.

The recipe list

Both authored pools show at once, headed recipe_catalog and port_bucket, because which pool a recipe is written into is the one place bucket membership is authored rather than derived — you have to be able to see the split. Each row carries a live lint stripe and its shape in brackets.

Two append buttons, one per pool. A new recipe starts with a single Fight stage.

Editing a recipe

Name it, choose its pool, then work the stage list. Two fields are derived and not yours:

DerivedFrom
bucketThe stage count: 1 → Coastal, 2 → Open Sea, more → Deep. The Port pool is bespoke-placed and exempt. A recipe cannot be filed in the wrong bucket, because it isn't filed.
revealsWhether the first stage reveals. An encounter reveals if and only if its first stage does.

Each stage row has its ordinal, a kind combo, a stock pool combo, and up dn x. Choosing Shop supplies a default pool; choosing anything else clears it — a pool is authored if and only if the primitive is a Shop, and the bake asserts it both directions. + stage appends a Reward, up to the stage maximum.

Order is meaningful: costs are authored ahead of the boons they pay for. Reordering with up and dn is a real authoring act, not a display preference.

Bake preview

Pick a zone, a depth and a seed, and the builder runs the recipe through the real bake and renders what each stage actually produced, slot by slot. This is where "is this encounter any good at this depth" gets answered — re-roll the seed to see the spread rather than one sample.

StageWhat the preview shows
FightThe opponent's hull, effective speed and output scaling, then every installed fitting with its slot, visibility, fire contribution and cargo.
OfferThe tier band, then each option with its showcase magnitude.
TradeThe bargain as baked: gain this for that.
ShopThe card count split into shelf and reserve, then each card with its tier and cargo price.
RewardThe cargo it pays.

The lint findings

The catalog's conventions are enforced by tests at odin test. They are checked here as you compose, so an anti-shape is a red line on the row you just wrote instead of a failing build twenty minutes later. One finding at a time, in the order the conventions are written.

FindingReason
UnnamedA name is not decoration: a recipe's identity is its shape plus its name.
Duplicate_NameAnother recipe already carries this name.
No_StagesA recipe must author at least one stage.
Shop_Without_A_PoolA Shop spec names the hold it sells from; the bake asserts it.
Pool_Without_A_ShopOnly a Shop authors a stock pool: no other primitive has one to draw from.
Cost_Behind_A_BoonA declinable cost behind a boon is a free escape from paying for it.
Duplicate_ShapeAnother recipe authors the same stage kinds: nothing downstream can tell them apart.
Catalog_Opens_On_A_ShopOnly the Port bucket opens on a Shop — a merchant earns its Shop by putting a stage in front of it.
One_Stage_Bucket_FullThe 1-stage bucket is capped, permanently: a further entry could only duplicate a shape.
Shape means the kind sequence, and nothing else

A differing stock pool does not rescue a shape collision. A baked shop stage carries its cards but not the pool that dealt them, so two recipes with the same kinds are one indistinguishable encounter on the map, in a snapshot, and to the recipe recovery that matches on kinds. That is stricter than authoring wants, and it is what the catalog's own test enforces — so a recipe this lint calls clean passes the catalog's tests unchanged.

Which stages count as costs: Fight and Trade, because they both cost something and can be declined, so their halt is a free exit from everything downstream. Shop is a boon despite spending cargo — it never halts.

3 · Rosters

Hostile archetypes, trade axes and stock pools. The two main surfaces lean on all three, so balancing items and encounters without them is half a job.

Archetypes

A hostile build is an ordered list of roster items, picked from combos over the live roster — so a dangling item name is unauthorable; an archetype holds an index, never a spelling. Order is authoring: placement is first-empty-fit into a template whose slots are exposed-first within each size, so an item placed earlier lands on deck and one placed later falls back to the concealed hold.

The right pane resolves that placement the way generation does and prints the resulting hull, weight and speed — and then fights it, because the roster's authoring rule has two walls and both are about how a fight with a starting player actually goes. The build is fought against a starting ship at Coastal, both sides holding, so what it measures is the damage the two loadouts produce rather than how escape was played.

CheckFails when
roundsThe fight resolves before the escape gate opens.
floorA starting player cannot scratch the build — a fight with no risk.
ceilingThe build sinks a starting ship before Break Off comes off the bench.
terminationThis build and a starting player cannot finish a fight at Coastal.
placementThe build asks for more slots of a size than the template has.

Trade axes

An axis carries no magnitudes — those are the site's swing — so it is authored purely as "what for what". Below the fields, the swing each zone would apply, and four guardrails:

FaultReason
UnnamedPresentation says which bargain this is from the name.
Name_CollidesThat name is taken by a roster item — a Trade is not a thing you install.
Hull_Is_Gain_OnlyNothing else in the game heals, and a trade that damages you is a Fight without the fight.
Same_Stat_Both_SidesBoth sides name the same stat, so the trade nets to nothing.

Speed is absent from the stat list entirely: it is a derived read-out of weight, so it is not tradeable.

Stock pools

The five holds. The set itself is closed — a pool reaches a node by being named by a recipe, so adding one is a catalog edit as well as a table edit — and this tab edits what each one is made of.

Unfiltered ≠ every family

The filtered checkbox is separate from the family set on purpose. Unfiltered means no filter, so an unfiltered shop keeps stocking a sixth tag the day one is authored. Ticking every box instead would silently freeze the pool at today's tag list.

depth is how many cards deep the hold is. Two derived read-outs follow: candidates, the roster items this pool may stock, and reserve, the cards behind the shelf — the only thing standing between a shop and exhaustion. At or below the shelf size the reserve reads as a shop that can be bought out in one visit, and if candidates fall short of depth the panel warns that a shelf will come up short.

4 · Ship & Constants

Read-only. Not the Forge's to edit, but on screen because everything else depends on them.

Ship template

Every slot with its size and base visibility, exposed-first within each size — which is what makes loadout order authoring. Then the pricing census derived from it.

Constants

Ship, budget and content constants as the game defines them: starting hull and speed, the budget's point, band and rates, the gate factors, the roster and encounter bounds.

Stakes by site

One row per zone and depth, one column per primitive's reading of it — opponent hull, power percent, offer quality, reward cargo, and the tier band. Then trade swing by zone.

The layout is a balance surface

The pricing census is derived by walking the real ship template. Re-sizing a hold re-prices every counting item in the roster — which is why the template sits here rather than being left implicit.

Ctrl+C on this surface emits a comment saying so, rather than a table line.

Getting the work out

There is no save. Ctrl+C copies the current row as the exact Odin line its table is written in, in the house style the tables already use — pasted rather than adapted.

The emit is also rendered, in a panel at the bottom of the surface, so you read the line before pasting rather than discovering it in your editor. Which row gets emitted depends on the surface:

SurfaceEmits
Item WorkbenchOne roster_item(…) line. Bulk is written only where it differs from the size's full contribution, and requires_exposed only when true — naming a default would say less than leaving it out.
Encounter BuilderTwo things: the @(rodata) stage array, and the catalog or port-bucket entry that names it. Both, because a recipe authored without its backing array would be a slice of nothing.
Rosters · ArchetypesThe item-name array plus the roster entry, in edit order.
Rosters · Trade / StockThe single table row.
Ship & ConstantsA comment saying these are read-only.

Two warnings the emit carries

An appended item emits with the count bump attached, because the count is what makes a miscount a compile error rather than silent:

// append to ship_item_roster, and bump the count:
roster_item(.Splash, "Chain Shot Rack", .Small, 40, {.Artifact}, {…}),

ITEM_ROSTER_SIZE :: 51

An edited existing row emits with the cost of that edit stated:

// WARNING: this replaces roster row 12, so every seed that draws it now deals a different item
roster_item(.Splash, "War Hound", .Small, 7, {.Beast}, {effect_phase_contribution(expr_below_hull_percent(50, 4))}),

Note the tree came back out as expr_below_hull_percent(50, 4) rather than as the four-node Gate it expands to: a subtree that still matches a preset emits as that preset's helper, which is what keeps the emitted roster reading like the roster it is pasted into.

The round trip

The tests embed the real tables and assert that every line the Forge emits is already in the shipped table, modulo formatting and the spelling order of a tag set. Re-reading emitted source through core reassembles the same tree, and so reproduces the verdict the tool showed you.

Workflows

Three things the tool is shaped around doing.

Balance an item to its band

  1. Select the row. The budget panel is already showing its equation.
  2. Read solve for magnitude, not the cost. It tells you the peak range that lands inside the band with everything else pinned.
  3. Set the tree's magnitude to something in that range. If the range is empty — high below low — the panel says so in red, and the fix is the weight, the size or the tier, not the tree.
  4. Check the three readings agree with your intent: showcase is what the player is promised, peak is what you are charged for.
  5. Ctrl+C, paste, run the tests.

Add an encounter

  1. + catalog recipe (or port). Name it — the lint faults an unnamed one immediately.
  2. Build the stage list. Watch the lint pane: it is checking the same conventions the catalog's tests check.
  3. Note the derived bucket. You do not choose it; the stage count does.
  4. Bake it at the zone and depth it will actually appear in, then re-roll the seed several times to see the spread rather than one lucky sample.
  5. Ctrl+C — remember it emits two pieces, the array and the entry.

Add a hostile

  1. Append an archetype and name it.
  2. Add items from the roster combos. Order is placement: earlier lands on deck, later falls to the concealed hold.
  3. Read the resolved placement, then both walls. All of it must be green — a build that cannot be scratched and a build that sinks you before you can run are both faults.
  4. If placement fails outright, the build wants more slots of a size than the template has; drop or resize an item.

Traps

Five things that will bite once each.

Editing an existing roster row re-deals every seed that draws it

The Forge only ever appends, so no index moves — but a shop's shelf and an Offer's options are drawn by indexing the roster. Change row 12 and every seed that dealt row 12 now deals something else. The item pane says so in amber the moment you diverge, and the emit repeats it. Appending is safe; editing in place is a deliberate act.

Closing the window is the only exit, and it discards everything

There is no save file. Copy what you want before you close it. Esc deliberately does not quit — it only leaves the field you are editing.

Sorting the roster does not renumber it

Every sort but the default reorders the view alone. The # column always shows the roster index, which is what a seed draws by.

A gate buried under arithmetic pays nothing

The budget discounts a condition in front of the magnitude, not one that is part of the tree's value. If your gate sits under a Mul, the panel says so plainly rather than announcing a discount you are not getting.

Opponent counts read zero outside a battle

A Count node set to the Opponent side reads the scouting report, which cannot see a concealed fitting — and outside a battle reads nothing at all. The tree editor says so beside the control.
